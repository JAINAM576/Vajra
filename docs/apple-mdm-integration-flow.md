# Apple MDM Integration Flow — Setup Reference

This document describes the full flow for standing up an Apple MDM server (using MicroMDM/NanoMDM) and integrating it with our existing custom backend, similar to our current Android DPM/activation-key flow.

---

## 1. High-Level Architecture

```
Our Backend (business logic)  <-->  MicroMDM / NanoMDM (MDM protocol engine)  <-->  Apple (APNs + device)
        (Vercel / other)                  (VPS, always-on)                        (Apple's infra)
```

- **Our backend**: handles credits, shopkeeper accounts, customer activation, payment logic. Stays on our current hosting (e.g. Vercel).
- **MicroMDM / NanoMDM**: a separate, always-on service that speaks Apple's MDM protocol (plist/APNs). We configure it, we do not need to modify its source code.
- **Apple**: push notification delivery + device management framework. We never talk to Apple directly — MicroMDM/NanoMDM does that on our behalf.

**Important constraint:** MicroMDM/NanoMDM must run on a persistent server (VPS/cloud instance), not serverless functions (e.g. Vercel), because it needs to stay alive continuously and hold local state (device records, push tokens, command queue).

---

## 2. Prerequisites (Apple-side credentials)

These must be obtained before MicroMDM/NanoMDM can function for real devices:

| # | Item | Where it comes from |
|---|------|----------------------|
| 1 | Apple Developer Program membership | developer.apple.com — done ✅ |
| 2 | MDM Vendor CSR Signing Certificate | Requested via developer.apple.com/contact — manual Apple approval, in progress 🔄 |
| 3 | CSR (Certificate Signing Request) | Generated locally, signed using item #2 |
| 4 | MDM Push Certificate (.pem + private key) | Generated by uploading CSR to identity.apple.com/pushcert |
| 5 | Public domain + valid HTTPS/SSL | We provide (e.g. `mdm.ourdomain.com`) |
| 6 | Profile-signing certificate | Self-signed or CA-issued, used to sign enrollment `.mobileconfig` files |

**Note:** Item #4 (the push certificate) is the actual credential MicroMDM/NanoMDM uses to authenticate to Apple's push service. It must be renewed annually or devices lose management silently.

---

## 3. Hosting Requirements

- A VPS or cloud instance capable of running a long-lived process (e.g. DigitalOcean, Hetzner, AWS EC2, Fly.io, Railway).
- Public domain (e.g. `mdm.ourdomain.com`) with DNS pointed at this server's IP — **not** at our Vercel deployment.
- Valid SSL certificate on that domain (Let's Encrypt is fine).
- Database for MicroMDM/NanoMDM's own device/command state (BoltDB default, or Postgres/MySQL for NanoMDM).

---

## 4. MicroMDM/NanoMDM Setup Flow

> Use **NanoMDM** (github.com/micromdm/nanomdm) for new builds — the original MicroMDM v1 repo is in maintenance mode as of end of 2025. Same maintainers, actively developed successor.

1. Provision the VPS, point DNS at it, set up SSL.
2. Install/run NanoMDM as a standalone service (binary or Docker container).
3. Pass in startup configuration:
   - Path to our push certificate (.pem) + private key
   - Our public domain
   - Database connection
   - An admin API token (we define this — used to authenticate our backend's calls to it)
4. Confirm the service is reachable publicly over HTTPS at our domain (test check-in endpoint responds).
5. Set up the companion enrollment/profile-signing piece (separate small tool alongside NanoMDM — generates and signs `.mobileconfig` enrollment profiles).

**We configure this via flags/env vars — we do not need to modify NanoMDM's source code for standard usage.**

## 5. Integration Flow with Our Backend

### 5a. Outgoing: Our backend → NanoMDM (sending commands)

- NanoMDM exposes a local REST API (e.g. on an internal port), authenticated with our admin API token.
- Our backend calls this API whenever business logic requires a device action — e.g.:
  - Customer enrolled → no action needed (device enrolls itself, see 5b)
  - Payment missed → backend calls NanoMDM API → "lock device X"
  - Payment resumed → backend calls NanoMDM API → "unlock device X"
- NanoMDM translates this into the real Apple push + plist command and handles delivery.

### 5b. Incoming: NanoMDM → our backend (device events via webhook)

- We configure a webhook URL in NanoMDM pointing to an endpoint on our backend (e.g. `https://ourbackend.com/mdm-events`).
- NanoMDM POSTs event data to this endpoint whenever something happens:
  - Device enrolls / checks in for the first time (`TokenUpdate`) → gives us a unique device identifier + push token
  - Device acknowledges a command (e.g. confirms it locked)
  - Device reports status changes
- Our backend receives this webhook and links the device identifier to the correct customer/shopkeeper record in **our own database**.

### 5c. Linking devices to customers

- Our enrollment profile (`.mobileconfig`) embeds a custom identifier (equivalent to our current Android activation key) when generated for a specific customer/shopkeeper.
- When the device checks in for the first time, that identifier — plus the device's unique push token — comes through in the webhook (5b).
- Our backend stores this mapping in our own database. This is the direct replacement for "activation key linked to phone" in our Android flow.

---

## 6. Two Separate Databases

| Database | Owned by | Contains |
|---|---|---|
| NanoMDM's DB | NanoMDM | Device push tokens, command queue, raw MDM protocol state |
| Our backend's DB | Us | Customers, shopkeepers, credit balances, payment status, device-to-customer mapping |

These are linked only by the **device identifier**, passed via webhook (5b) and referenced in our API calls (5a).

```
[Shopkeeper buys credit]
        |
[Our backend generates enrollment profile w/ embedded customer ID]
        |
[Customer installs profile on iPhone] --(auto)--> [NanoMDM check-in]
        |
[NanoMDM webhook] --> [Our backend saves device ID <-> customer link]
        |
   ... time passes ...
        |
[Payment missed in our backend] --> [Our backend calls NanoMDM API: lock device]
        |
[NanoMDM --> Apple push --> iPhone wakes up --> calls NanoMDM --> gets lock command --> executes]
        |
[NanoMDM webhook confirms lock] --> [Our backend updates status]
```
